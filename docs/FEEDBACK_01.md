## 1. ベースが歩けていない（優先度: 最高）

### 受け取り方の訂正

「逆にかっこいい」は皮肉。**ベースラインが実用に耐えていない**という指摘として扱う。当初これを「自由さは残しつつ基準点を足す」と書いたのは読み違いだった。自由さではなく、**でたらめに動いている**のが問題。

### コードを読んで見つかった欠陥

**(a) 中間の拍で、近い音がほとんど優先されていない**（[bass.ts の pickMiddleNote](../src/music/bass.ts)）

候補を「直前の音に近い順」に並べたあと、`1/(index+1)` の重みで抽選している。候補はコードトーン＋スケール音で最大8個あるので、重みの合計は約2.7。**いちばん近い音が選ばれる確率は37%しかない**。残り63%は、より遠い音（最大で6半音先）へ跳ぶ。これが1コードにつき数回起きるので、線が歩かずに飛び回る。

ウォーキングベースは「隣へ歩く」のが前提なので、ここが最大の原因。

**(b) 強拍と弱拍が区別されていない**

仕様書§6は中間の拍を「コードトーンかスケール音」としか書いていない。実装も全部の中間拍を同じ扱いにしている。実際は**3拍目（もう1つの強拍）はコードトーン**であるべきで、そこにスケール音が自由に入ると、和音の輪郭が消える。「どこを弾いているかわからない」の直接の原因はこれ。

**(c) 1小節に2コードあると、半分がアプローチ音になる**

`Dm7 G7 | ...` のように1小節2コードだと各コード2拍。実装は「コードの最後の拍＝アプローチ音」なので、**2拍のうち1拍がアプローチ音**になる。半音で滑り込む音が全体の半分を占めると、調性感が薄れて漂って聞こえる。

**(d) 音域を漂う**

`RANGES.bass` は E1–G3（28–55）で2オクターブ強ある。オクターブは「直前の音に最も近いもの」で決めているだけなので、**中心へ戻す力が無い**。何小節も進むうちに上端や下端へ寄っていき、コードの頭のルートも回によって違うオクターブで鳴る。これも形が見えない一因。

### 決めたこと

1. **中間拍は原則として順次進行**。候補を直前の音から±4半音以内に絞り、重み付けも急峻にする（`1/(i+1)` ではなく指数的に）。跳躍は例外にする
2. **3拍目はコードトーン優先**（ルート・3度・5度・7度）。スケール音は弱拍（2・4拍目）に回す
3. **1小節2コードのときは、アプローチ音を毎回入れない**。確率で入れる（既定 0.6 程度）。残りはコードトーン
4. **音域を狭めて中心へ戻す力を入れる**。walking の実用域は E1–E3 くらい。中心から離れるほど、中心方向の候補を優先する弱いバイアスを足す
5. **連続する2音の跳躍に上限**を設ける（原則5半音以内。コードの頭でのみ例外を許す）
6. **コーラスの1小節目の1拍目は必ずルート**（確率1.0）。それ以外の小節の頭は現行どおり
7. **既定の進行を4小節にする**。`DEFAULT_PROGRESSION`（[src/App.tsx:12](../src/App.tsx:12)）は3小節なので、ループすると3小節周期になり、耳が小節を数えられない

1〜5がベースライン自体の作り直し、6〜7が形を見せるための補強。**1と2だけでもかなり改善するはず**なので、そこから着手する。

### テスト

現行の `bass.test.ts` は「音域内」「1拍1音」「同じ音が3回続かない」しか見ていないので、歩けているかを測れていない。以下を足す。

- 連続する2音の音程が5半音以内である割合が9割以上
- 3拍目がコードトーンである割合が8割以上
- 1コーラス内で使う音域の幅が1.5オクターブ以内

## 2. バドっぽくない（優先度: 高）

### 原因は特定できた。スコア関数の「多様性」項

[src/music/score.ts:52](../src/music/score.ts:52) の `varietyPenalty` が、**同じ family が続くことを減点している**。

```
直近3つに同じfamilyが2回以上あれば +1、3回とも同じなら +2
```

これは厚いボイシングでは正しい（同じ型が続くと単調になる）。しかし Powell では**逆**。Powell の左手は R7 と R3/R10 をひたすら繰り返すのが様式そのもので、「毎回ちがう型を選ぶ」と Powell ではなくなる。

つまり、第1段階で汎用のスコアをそのまま Powell に適用したのが誤りだった。

### 決めたこと

- **Powell / shell3 では `varietyPenalty` を無効にする**（重み0）。様式として反復が正しいため
- **R7 と R10 を優先する重みを入れる**。利用者の要望どおり、この2つが Powell の中心。`constants.ts` に語彙ごとの選好重みを追加する

```ts
export const POWELL_FAMILY_BIAS: Record<string, number> = {
  'powell-r7': -1.2,    // 負の値 = 選ばれやすい
  'powell-r10': -1.0,
  'powell-r3': 0.4,     // 低い位置の狭い3度は Powell が避けた響き。控えめに
  'powell-r6': 0.6,
}
```

- **R3（近接の3度）を積極的に減らす**。Powell が広い音程を使った理由は「低い位置で濁らないため」（[VOICING_RESEARCH.md §8](VOICING_RESEARCH.md)）なので、3度を使うなら R10 のほうが様式に合う。R3 は音域の上のほうでのみ許可する案も検討する

## 3. 何コーラス目からか変になる（優先度: 高・要調査）

「何コーラス目**から**」という言い方から、**1周ごとに何かが蓄積している**と考えられる。単発のランダムの当たり外れではない。

### 疑っている順

**(a) 再生スケジューラの時刻が後ろ倒しになっている（本命）**

[src/music/render/audio.ts](../src/music/render/audio.ts) の `startPerformanceLoop` は、次のコーラスの開始時刻を `nextStart += chorusSeconds` で積み上げ、`setTimeout` を `(chorusSeconds - 0.4) * 1000` で仕掛けている。

ここに **`nextStart` が現在時刻より過去になっていないかの確認が無い**。タイマーが遅れた場合（タブの間引き、GC、あるいは毎コーラス走るビームサーチ自体が重い場合）、`nextStart` が `ctx.currentTime` を下回り、**そのコーラスの音が全部「過去の時刻」で予約されて一斉に鳴る**。これは「変になる」の聞こえ方と一致するし、ずれが累積するので「何コーラス目から」とも一致する。

対策案: `nextStart = Math.max(nextStart, ctx.currentTime + 0.05)` を入れ、ずれたぶんはその周で吸収する。

**(b) オシレーターの後始末が追いつかず負荷で崩れる**

`activeOscillators` は `onended` で除去しているが、ループが続くと配列が伸び続ける可能性がある。長時間再生でのCPU負荷を確認する。

**(c) ボイシング側の問題**

`randomness` が効いた結果、まれに極端な候補が選ばれている可能性。ただしこれは周回に依存しないので、「何コーラス目から」の説明にはならない。優先度は低い。

### 実際の原因（調査済み・仮説は外れていた）

ブラウザで計測した結果、`nextStart` が**過去になることは無かった**。逆に、`nextStart - ctx.currentTime` が際限なく**開いていった**。

```
chorus0=0.080s  chorus1=0.481s  chorus2=0.861s
chorus3=1.246s  chorus4=1.634s  chorus5=2.022s
```

1周ごとに約0.4秒ずつ増えている。原因は、次の `scheduleChorus` までの待ち時間を `chorusSeconds - 0.4` という固定値で計算していたこと。`nextStart` は毎周 `chorusSeconds` 進むのに、実時間は `chorusSeconds - 0.4` しか進まないので、両者の差が毎周0.4秒ずつ永久に開く。

音の開始時刻自体はズレないが、**実際に鳴るよりずっと先の分まで毎周オシレーターを作り続ける**ことになり、未再生の `OscillatorNode` が積み上がる。これが「何コーラス目からか重くなって変になる」の正体。

修正は、待ち時間を毎回「実際に残っている先読み時間」から逆算する形に変更。修正後は14周まわしても 0.395〜0.417秒で安定した。当初の下限クランプも保険として残してある。

### 調査の手順（実施済み・記録として残す）

1. 各コーラスの先頭で `ctx.currentTime` と `nextStart` の差をログに出す。差が縮んで0に近づいていれば (a) で確定
2. (a) なら上記の下限クランプを入れて、20コーラス以上流して再現しないことを確認する
3. それでも再現するなら (b) を測る

## 4. Powell の Dm7 に シ(B) が入る（優先度: 高・原因確定）

### 原因

[src/music/vocab/powell.ts:52](../src/music/vocab/powell.ts:52)

```ts
const SIXTH_QUALITIES: ChordQuality[] = ['major', 'major7', 'minor7'] // minor7はm6として使う
```

`minor7` に R6 を許しているので、Dm7 に対して `D + B`（1と6）が作られる。これは Dm6 の響きであって Dm7 ではない。ii-V-I の ii として鳴らすと、コードを決定づける b7（C音）が消えるため、利用者の言うとおり「変」。

仕様書 §4 の「R6 → major, major7, minor7（m6として）」という記述が誤りだった。

### 決めたこと

- **`SIXTH_QUALITIES` から `minor7` を外す**。R6 はトニックのメジャー系（`major`, `major7`）のみ
- 仕様書 §4 の表も直す

## 5. 声部が近いところへ進行しない（優先度: 最高・原因確定）

指摘:「なんか全体的に声部が近いところに進行せんのが気になる」「4小節目から1小節目は進行として考えられていない感じ？ 1〜4小節でジェネレートしているから」

### (a) 候補がそもそも存在しない

既定の進行 `Dm7 G7 | Cmaj7 | A7alt` を thick で計測した結果。

| コード | 組み立てた数 | 演奏可能性を通過 |
| --- | --- | --- |
| Dm7 | 15 | **6** |
| G7 | 4 | **1** |
| Cmaj7 | 8 | **4** |
| A7alt | 12 | **7** |

**G7 の候補は1個しかない。** ビームサーチは選択肢が1つなら何も選べないので、前後がどうであろうとその1個が置かれる。「声部が近いところへ進行しない」の原因は、スコア関数でも重みでもなく**選択肢の不在**。

`SEARCH.candidatesPerChord: 40` という絞り込みは、候補が最大15個しかない現状では一度も効いていない。

原因は2つ。

1. **語彙が足りない**。第1段階は rootless と Powell だけで、Quartal / So What / UST / Drop2 / Cluster は第2段階送りにした。これらは「同じコードを別の形で置く」ための語彙そのもので、無いと選択肢が増えない
2. **組み立ててから落としている**。落ちた理由は `handsCrossed`（手が交差）、`handSpanMax`（幅超過）、`handGapMax`（左右が開きすぎ）、`lowInterval`（低音の濁り）で、組み立てた数の5〜7割が落ちる。**先に条件を満たす配置を作る**のではなく、作ってから捨てているので歩留まりが悪い

### (b) ループの継ぎ目は、進行として扱われていない — 指摘のとおり

計測値（同じ進行、randomness 38%、12回）。

- 進行の中の平均移動量: **14**
- 4番目 → 次コーラスの1番目の移動量: **24**（幅 10〜34）

継ぎ目は進行内の約1.7倍動いている。理由は2つあり、指摘より深い。

1. **1テイクの中でも、最後→最初は評価されていない**。ビームサーチは1番目のコードを「前が無い」として音域だけで評価する（[take.ts](../src/music/take.ts)）。末尾から先頭へ戻る接続はスコアに一切入らない
2. **ループ中は毎コーラス、完全に独立したテイクを引き直している**（[App.tsx](../src/App.tsx)）。つまり継ぎ目は「無関係な2つのテイクの端どうし」。1を直しても、これを直さないと継ぎ目は繋がらない

### 決めたこと

- **語彙を増やす**（第2段階の前倒し）。候補が1個では何をしても改善しない。ここが最優先
- **演奏可能条件を満たす配置を先に作る**方式へ変える（生成してから捨てない）
- **循環として探索する**。末尾→先頭の接続をスコアに入れる
- **次コーラスの1番目は、前コーラスの最後のボイシングを「前のコード」として評価する**。ループ再生と複数コーラス書き出しの両方に効く

## 記録

- 今回のフィードバックで、**スコア関数を語彙ごとに切り替える必要がある**ことがわかった。「厚さプリセットはボイシング・音域・リズムをまとめて切り替えるシーン」（[DESIGN_v0.2.md §15.3](DESIGN_v0.2.md)）に、**スコアの重み**も含める必要がある
- 「逆にかっこいい」は皮肉。**感想の語調で深刻度を判断しない**こと。今回は最初これを褒め言葉と読み違えて、対応を「基準点を足すだけ」に見積もっていた。実際にはベースライン生成の作り直しが要る
- ベースの欠陥は、仕様書§6が「中間の拍: コードトーンかスケール音。直前から2半音以内を優先」としか書いておらず、**強拍と弱拍を区別していなかった**ことに由来する。音楽的な役割を度数だけで書くと、こういう抜けが出る
